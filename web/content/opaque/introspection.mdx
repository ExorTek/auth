# Introspection & Revocation

Framework-agnostic HTTP handlers — works with raw Node, Express, and
Fastify (unwraps `reply.raw` automatically, same trick
[`@exortek/jwks`'s handler](/jwks) uses). Both assume the request body
is already parsed (Express `json()` middleware, Fastify's built-in
JSON parsing).

Handlers return `{ status, body, headers }` — the caller owns the
response. That lets you add CORS, request-id, envelope the body, or
send it any way your framework prefers, without the handler ever
touching `res` itself.

```js
import { introspectionHandler, revocationHandler } from '@exortek/opaque';

const introspect = introspectionHandler({ store });
const revokeRoute = revocationHandler({ store });

// RFC 7662 — always 200, active: false for anything invalid so a
// caller can't distinguish "unknown" from "expired" from "revoked".
app.post('/oauth/introspect', async (req, res) => {
  const { status, body, headers } = await introspect(req);
  res.set(headers).status(status).json(body);
});

// RFC 7009 §2.2 — always 200 {}, whether or not the token existed.
// The RFC explicitly forbids error responses here: the client cannot
// handle them in a reasonable way.
app.post('/oauth/revoke', async (req, res) => {
  const { status, body, headers } = await revokeRoute(req);
  res.set(headers).status(status).json(body);
});
```

Fastify: same `handler(req)` call —
`reply.headers(headers).code(status)` then `return body`.

Every response's `headers` already carries the RFC-recommended
defaults: `Content-Type: application/json`, `Cache-Control: no-store`,
`Pragma: no-cache` (RFC 6749 §5.1 sensitive-response guidance).

<Callout type="warning">
  **Both endpoints MUST be authenticated.** RFC 7662 §2.1 and RFC 7009
  §2.1 require the caller to authenticate — introspection is only safe
  for a resource server you trust, revocation is only safe for the
  client the token was minted for. Anonymous introspection lets an
  attacker scan for valid tokens; anonymous revocation lets any observer
  of a leaked token burn it. Gate the route before mounting the handler
  — nothing in this package does it for you.

  Whatever you pass to `create({ metadata })` is echoed back by
  introspection — do NOT store PII, secrets, or internal identifiers
  there. Prefer the RFC 7662 §2.2 claim names (`sub`, `scope`,
  `client_id`, `exp`, `token_type`, `iss`, …).
</Callout>

```js
// Minimal Express gate — replace with your real auth.
import basicAuth from 'express-basic-auth';
app.post(
  '/oauth/introspect',
  basicAuth({ users: { 'resource-server': process.env.INTROSPECT_SECRET } }),
  introspectionHandler({ store }),
);
```

## Options (both handlers)

| Option       | Default    | Notes                                    |
| ------------ | ---------- | ------------------------------------------ |
| `store`      | —          | Required.                                |
| `hashAlgo`   | `'sha256'` |                                           |
| `tokenField` | `'token'`  | Field read off the parsed request body.  |
| `onError`    | —          | `(err) => void` — called if `store.get`/`store.delete` throws. The handler still responds with the no-oracle default so the store's health never leaks. |

### Wire format

RFC 7662 §2.1 defines the request as `application/x-www-form-urlencoded`
with `token` and optional `token_type_hint`. The handler reads
`req.body[tokenField]`, so it accepts whatever your framework has
already parsed — JSON out of the box (Express `express.json()`,
Fastify built-in). To accept form-encoded input, register the
appropriate body parser (Express `express.urlencoded()`, Fastify
`@fastify/formbody`); `tokenField: 'token'` still works.
`token_type_hint` is ignored — an opaque reference token has one type.

### Recommended metadata claims (RFC 7662 §2.2)

Whatever you pass to `create({ metadata })` is what introspection
returns to the caller. Prefer the RFC claim names so any standard
resource server understands the response:

| Claim         | Meaning                                             |
| ------------- | --------------------------------------------------- |
| `sub`         | The user the token was issued for.                  |
| `scope`       | Space-separated OAuth scopes.                       |
| `client_id`   | The OAuth client the token was issued to.           |
| `exp`         | Expiry, seconds since epoch.                        |
| `iat`         | Issued-at, seconds since epoch.                     |
| `token_type`  | e.g. `"Bearer"`.                                    |
| `iss`         | Issuer URL.                                         |
| `username`    | Human-readable identifier.                          |

The response's `active` field is always ours — a `metadata.active` you
stored gets shadowed by the handler.

<Callout type="info">
  Both endpoints deliberately respond `200` for every outcome — RFC
  7662 §2.2 and RFC 7009 §2.2 both call this out: leaking a distinct
  status code for "token doesn't exist" vs "token is expired" vs
  "token was revoked" hands an attacker a free oracle for guessing
  valid-looking tokens.
</Callout>
